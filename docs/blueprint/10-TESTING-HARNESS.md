# 10 · 测试、Harness 与质量门禁

版本：2.0｜日期：2026-10-02｜目标：证明需求被检验，而不只是“测试执行成功”。

[返回总入口](../../README.md) · [流程](11-FEATURE-WORKFLOW.md) · [模板](12-TEMPLATES.md)

## 1. 三个不能混淆的对象

**验收场景**定义系统应该如何表现；**可执行测试**用输入、操作和断言检验它；**执行证据**记录测试确实在指定环境运行以及结果。文件存在、ID 对应、覆盖率或 Agent 口头承诺都不是三者同时成立的证明。

本母版采用需求先明确、小步测试驱动实现；这是一套项目工作约定，不声称任何其他流程都不合格。NIST SSDF 是可融入不同生命周期的安全开发框架，不规定本仓库这些目录和唯一五步编码顺序。[S33](SOURCES.md#s33)

## 2. 测试分布

| 范围 | 位置 | 证明内容 |
|---|---|---|
| Web 单元/组件 | 源码旁或 Next 明确测试目录 | 纯逻辑、渲染、交互局部行为 |
| Web 应用集成 | `apps/web/tests/integration/` | 前端组合、适配器与状态 |
| 小程序单元 | `apps/miniprogram/tests/unit/` | 可隔离的 TS 状态和映射 |
| 小程序打包 | `apps/miniprogram/tests/build/` | 页面/组件/分包/SDK 真正进入产物 |
| Python 模块 | `apps/backend/tests/modules/<module>/` | domain/use case/DB/API 分层行为 |
| 后端跨模块 | `apps/backend/tests/integration/` | 模块协作和事务边界 |
| 契约、安全、迁移 | 后端对应 `tests/` 子目录 | 运行接口、安全边界和数据演进 |
| 公共 SDK | `packages/ts/api-client/tests/` | 编码、解析、跨 transport 语义 |
| 全栈 Web | `tests/e2e/web/` | 实际浏览器 + 后端 + 测试数据 |
| 全栈小程序 | `tests/e2e/miniprogram/` | 小程序运行环境 + 实际后端 |
| 跨进程/队列 | `tests/system/`，按需 | 异步副作用、故障和恢复 |
| 整仓检查 | `tests/repository/` | 文档、workspace、生成器、规范工具 |

不重复复制同一测试凑层数；同一需求可以由多个层次的不同断言共同证明。

## 3. Test Spec 的最小字段

稳定 requirement/scenario ID、需求来源、前置条件、输入/操作、预期返回、状态变化、禁止副作用、错误/权限契约、适用风险和 oracle 来源。

团队 YAML 格式由项目自己维护并校验；不是某个现成行业通用 schema。测试中的 requirement marker/metadata 也需要框架插件或检查器实现，不能凭空假定写一个字段就自动产生追踪。

追踪表从测试和 spec 生成，不再人工维护第二张 Excel 或 Markdown 对照表。链接存在证明“关联”；语义有效性仍需下述验证。

## 4. 正向、反向、边界与故障矩阵

| 维度 | 例子 | 断言重点 |
|---|---|---|
| Positive | 满足条件的合法操作 | 正确输出与目标状态，不影响无关对象 |
| Negative | 无权限、非法状态、输入违反约束 | 正确拒绝、状态不发生禁止变化 |
| Boundary | 最小/最大、刚好过期、空列表 | 两侧及等号语义 |
| Malformed | 非法编码、缺字段、未知字段 | 协议与校验错误正确 |
| Full fail | 适用依赖在所有允许尝试中持续失败 | 有界终止、无假成功、不漏资源 |
| Fail then pass | 第一次失败、后续允许尝试成功 | 重试受控、没有重复最终副作用 |
| Partial fail | 多步中后段失败 | 回滚/补偿/可恢复状态符合契约 |
| Concurrency | 两主体同时更新、状态变化 | 不变量、隔离与冲突行为 |
| Duplicate | 同幂等 key 同请求/不同请求 | 结果复用/冲突与副作用次数 |
| Isolation | 改对象 ID、换组织、缓存命中 | 数据和操作范围不越界 |
| Cancellation | 用户退出、超时、任务取消 | 停止/忽略过期结果与清理 |
| Recovery | 重启、消息再投递、连接恢复 | 状态一致、不无穷循环 |

不是每个功能都需要所有维度。没有重试的纯函数不需要 Fail then pass；用 `N/A + 原因` 代替捏造场景。Full fail 不是要求整个测试套件全红，而是某项运行故障在允许范围内持续失败。

## 5. Red → Green 不等于故障恢复

TDD 的 Red 是目标行为未实现导致测试按预期失败；Green 是实现之后通过。因为语法错误、导入错误或服务没启动而失败，不自动证明测试检验了目标需求。

运行时 Fail then pass 是依赖第一次失败、之后成功的业务恢复场景。这两个概念应在报告中分开，不用“我先运行失败了”充当重试策略已经测试。

## 6. Oracle：预期从哪里来

Oracle 来自审查过的需求、不变量、可信参考或独立计算，不是当前实现输出。数字与字符串比较可以确定性完成；属性、关系和状态用规则/不变量断言；UI 视觉用批准基准与人工复核；非确定性模型输出需要另建评价方案。

不能把所有 correctness、completeness 或“符合需求”交给 LLM 自评分。LLM 可以发现遗漏和建议反例，但不是覆盖率、权限正确性或发布通过的唯一裁判。

纯代码覆盖率衡量执行到哪里，不能证明断言有效；snapshot 可能只记录现状，更新快照前仍要判断正确性。不能批量更新快照以消除回归。

## 7. Harness 必须证明测试有检出力

本规范区分三个维度，不把它们包装成某个行业认证等级：

**关联性：** 需求 ID 能找到实际执行的测试，测试覆盖正确入口和数据。

**断言有效性：** 检查返回、状态、范围和禁止副作用，不只检查函数调用发生或 status 是错误。

**检出力：** 对关键规则构造受控反例/变异，指定测试应识别它。Harness 负责运行和保存差异，而不是只存录像和日志。

建议的隔离验证流程：

```text
干净基线执行通过
  → 在临时 worktree/沙箱应用一个受控故障
  → 验证故障已实际改变目标行为
  → 运行应检出它的指定测试
  → 确认因目标断言失败，而非无关语法/环境失败
  → 记录证据，丢弃临时变体
  → 原基线再确认没有被修改
```

不在生产代码永久保留“关闭权限”的隐藏开关，只为 mutation 方便。隔离环境不得携带真实生产凭据。

## 8. 删除资源的完整例子

假设业务契约为“有权主体可删除未锁定资源”。这是示例，不代表所有项目必须使用同组织授权或物理删除。

| 场景 | 必须断言 |
|---|---|
| 有权限且未锁定 | 成功响应；目标按契约删除/变更；无关数据不变 |
| 未认证 | 契约错误；无禁止写入、无删除成功消息 |
| 无权限 | 授权被拒绝；目标状态不变；没有外部删除 |
| 不在授权范围 | 不泄露受保护数据；无跨范围修改 |
| 已锁定 | `CATALOG.RESOURCE_LOCKED`；仍锁定且未删除 |
| 提交前 DB 失败 | 无已提交的删除；无不一致成功结果 |
| 重复调用 | 按删除/幂等契约处理，不凭空假定一定返回同状态码 |

定向反例：移除授权 → deny 测试失败；移除锁定校验 → locked 测试失败；在拒绝前写库 → 副作用断言失败；无论结果都返回成功 → 错误响应测试失败。

一个变异存活可能是测试无效、场景不可达、变异等价或适配问题，需要分类；不能立即说实现必错。少量变异被检出也不是 100% 语义正确证明。

## 9. 测试替身、真实集成与确定性

单元测试用假端口隔离外部依赖；集成测试连接与生产语义一致的数据库。PostgreSQL 的事务、锁和约束不能由 SQLite 代替证明。

假服务必须遵循真实接口，且不是第二套业务实现。关键接口契约在真实服务上验证；客户端 mock 无法证明 Python API 已实现。

时钟、随机数、外部依赖应可控制。避免用任意 sleep 当同步保证；等待可观察状态并设总期限。并行测试隔离数据、账号和端口，失败保留可重现种子。

属性测试可以扩展输入空间，例如 Hypothesis 根据声明生成测试输入；其适用性仍依赖正确属性定义。[S31](SOURCES.md#s31) Web E2E 优先验证用户可见行为并保持测试隔离，参考 Playwright 的官方实践。[S32](SOURCES.md#s32)

## 10. 合并和发布门禁

| Gate | 合并最小要求 | 发布追加要求 |
|---|---|---|
| Source/Build | lint、typecheck、锁一致、已选客户端构建 | 受控镜像/小程序制品与版本 |
| Contract | 生成无漂移、运行接口与 Problem | 支持客户端兼容与 smoke |
| Behavior | 当前切片单元/集成/关键 E2E | 关键业务回归与风险场景 |
| Security | 权限/范围/秘密扫描、关键拒绝反例 | 目标环境、身份系统与审计检查 |
| Database | 新迁移与约束、支持旧版本升级 | 恢复/回滚或前向修复方案 |
| Architecture | 前后端/分包边界、违规检出 | 运行拓扑与部署一致 |
| Spec | 所有必需要求有有效测试或明确阻塞 | 未解决风险需批准，不假装通过 |
| Evidence | commit、命令、退出码、报告 | 环境、制品 digest、责任人 |

质量数字由项目风险确定，不预设“覆盖率 100% 才专业”或“80% 就一定合格”。所有强制 gate 失败/不可运行都阻止对应的完成声明。

## 11. 执行证据状态

`PASS`：确实运行并满足断言。`FAIL`：运行但违反预期。`BLOCKED`：所需环境/权限缺失等无法验证。`NOT_RUN`：尚未执行。`N/A`：经明确范围判断不适用并给理由。

报告必须包含工具与配置版本、commit、环境、执行命令、退出码、测试集合、产物位置、限制。对 GUI/真机人工检查，记录步骤和实际观察，不伪造自动退出码。

`.artifacts/` 为生成证据，不进源代码；必要证据上传 CI 制品并定义脱敏与保留时间。历史审计可保存摘要，但不能从旧 PASS 推断新 commit 也通过。

## 12. 不允许的“绿色”

空测试通过、catch 所有异常、把失败改 skip、弱化断言、当前输出复制为 expected、mock 掉正要验证的边界、仅检查错误返回却忽略副作用、只在浏览器测小程序替代页，以及 Agent 在未执行时说“全部通过”。

本包规定这些检查的责任，没有附带通用测试生成器或 Harness 实现；真实项目必须实现并验证检查器本身。
