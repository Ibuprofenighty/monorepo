## 1. 先设计规则，随功能交付实现

AuthN 解决“凭据代表谁”；AuthZ 解决“此主体能否对该资源执行该操作”。不是所有已登录用户都有相同权限，前端隐藏按钮不能代替服务端授权。OWASP 要求最小权限、默认拒绝和在正确位置检查访问控制。[S19](SOURCES.md#s19)

规则在需求/契约设计时明确，代码和测试随纵向切片完成。既不把权限留到全项目收尾，也不要求先造一个全能身份权限平台才能开发首个业务功能。

## 2. 唯一权威与目录归属

| 职责 | 位置 | 规则 |
|---|---|---|
| 可信主体表示 | `kernel/identity.py` | 与 HTTP、Keycloak/微信协议解耦 |
| 权限接口与决策类型 | `kernel/authorization.py` | 不装具体策略存储 |
| 请求身份验证 | `platform/authn/verifier.py` | 凭据验证完成才建立 Principal |
| 远程授权调用 | `platform/authz/client.py` | 仅远程方案启用；不复制政策 |
| action 与资源事实构造 | 模块 `application/access.py` | 事实来自可信后端状态 |
| 最终 enforcement | 受保护 use case | 所有入口覆盖，不交给客户端 |
| 本地政策权威 | `modules/access/`，仅本地方案 | 只有一个最终决策来源 |
| 独立政策权威 | `apps/authorization/` 或外部服务 | 本仓库不维护时不建空壳 |

本地与远程实现是初始化选项，不是两个同时维护、故障时互相猜测的生产策略。单一来源允许版本化只读分发或受控缓存，但需有清晰的有效性、撤销和故障语义。

## 3. 已确定的双塔授权项目

对沿用“薄 Keycloak AuthN library + 独立 Authorization Service”的项目，默认继续使用已批准边界，不在新母版里偷偷替换成 endpoint 内嵌 RBAC 或对象 ACL。

主体塔描述 application/organisation/group/person、角色及其一般权限；不保存对象列表或逐对象 ACL。资源塔描述 folder/object、所属范围与资源事实；不保存 person/group 白名单。决策时由权威结合两侧事实和一般规则。

`application/access.py` 可提供 action 与资源事实，但不能另写一套最终政策。没有一般规则支持的特殊 person/group—object 授权，不应由开发 Agent 临时加入。

这是特定项目的已选模型，其他项目可在选型表明确不同模型；不能把双塔强加给所有简单项目，也不能在选定双塔的项目中私自扩张范围。

## 4. 身份输入与会话

验证 JWT 时要按真实身份契约检查签名、签发方、受众、期限和允许算法；不是 decode 出 claims 就完成认证。角色/权限 claims 是否可用、多久更新，由权威与撤销策略决定，不因 token 中出现字符串便永久信任。

浏览器会话方案明确 cookie 属性、CSRF 防护、刷新、撤销与跨域行为；凭据型 cookie 场景不能只靠 CORS 当作完整安全控制。会话管理基础原则参考 [S20](SOURCES.md#s20)，具体方案由项目威胁模型决定。

Next BFF 可以管理 Web 会话与向 Python 转发所需身份，但不得因请求来自 BFF 内网就接受任意 `X-User-ID`。必须明确并验证可信凭据或受保护的服务身份及委托语义。

小程序采用 wx.login code → 服务端验证 → 内部用户映射 → 业务会话。客户端传来的 openid、organisation、role 不能作为未经验证的身份事实；session_key 不是业务登录 token，也不返回给客户端作为长期通行证。平台登录接口依据见 [S23](SOURCES.md#s23)。

## 5. 决策和执行

对于每个受保护操作，定义：主体来源、action、资源定位、可信属性、决策权威、拒绝/未知/错误行为、执行后审计。

授权权威不可用时，本母版默认拒绝受保护操作并返回受控依赖错误；不能 fail-open，也不能将技术故障一律表述为“用户无权限”。离线缓存等特殊要求必须单独批准，定义最大陈旧时间和撤销风险。

读取列表、计数、搜索、导出、附件下载、后台任务都需要范围控制。不能只保护写入，不检查可泄露信息的读路径。

## 6. 并发与拒绝无副作用

授权通过后资源所属范围、锁定状态或政策可能发生变化。为高风险操作决定版本条件更新、锁、事务内复验或授权有效期；不要把第一次 check 当作永远有效。

拒绝意味着没有被禁止的业务写入、付款、发信、消息发布、工具执行。允许独立的安全审计和必要指标，因此不能把“拒绝后所有存储都绝对不变”当作错误断言。

资源事实的最小读取也要遵守披露边界；不能先发出含敏感数据的事件再发现无权限。对不可回滚的外部操作，权限与必要校验必须在执行之前完成。

## 7. 配置与 secret

| 信息 | 权威入口 |
|---|---|
| 后端配置类型、校验 | `platform/config/settings.py` |
| 浏览器公开配置 | 客户端 `shared/config/env.ts` |
| 小程序公开构建配置 | 小程序构建输入与 `src/shared/config/` |
| 本地样例 | 根 `.env.example` |
| 部署样例 | `infra/config/` |
| 真实 secret | 环境注入或秘密管理系统 |

样例不承载实际密码。Vite `VITE_*` 等会进入客户端产物，不能包含服务端 secret。[S06](SOURCES.md#s06) Next server-only 数据不要经组件 props、日志或公共导出泄露；服务端运行不自动等于数据不会到客户端。[S08](SOURCES.md#s08)

配置解析失败要给出安全的字段说明，不把实际秘密回显到 CI 日志。测试覆盖缺失值、无效值、错误环境和危险默认值。对生产身份、数据库、上传密钥不提供会静默连到错误环境的 fallback。

## 8. 企业 AI 能力的可选扩展

只有项目真的包含 LLM/Agent 能力才启用。沿用四层职责：Detection 产出发现；Policy Plane 定义政策与最终判定；Gateway/Orchestrator/Executor 执行；Audit/Telemetry 记录证据。

规则权威集中不意味着 Gateway 没有预算和 rate limit。Gateway 仍可执行限流、预算预留/结算、路由和拒绝；Redis 可承担原子计数等运行状态。不要让多个组件各自维护互相冲突的预算政策。

工具 sandbox 的超时、幂等、资源预算和权限是执行边界，不能依靠 LLM 自觉遵守。具体目录与协议由该项目专门设计，不把所有 AI 项目硬塞进万能 `platform/ai.py`。

## 9. 安全验收矩阵

| 维度 | 必须有的证据 |
|---|---|
| AuthN | 有效、缺失、过期、错 issuer/audience、伪造等适用场景 |
| AuthZ | allow、deny、未知决策、权威失败、范围变化 |
| 隔离 | 换资源 ID、列表/计数/导出、缓存、后台路径 |
| 所有入口 | HTTP、worker、CLI 的受保护用例不能绕过 |
| 副作用 | deny 不写业务状态、不发成功消息，不触发外部操作 |
| 配置 | secret 不进 Git、镜像、前端包、日志 |
| 会话 | 撤销、刷新并发、退出、跨用户污染与 CSRF 等适用攻击 |
| 并发 | 授权或资源变化的窗口已定义并测试 |

单元 allow/deny 测试不能替代真实集成边界；mock authorizer 只能证明用例如何处理判定，不能证明远端身份与策略系统实际正确。
